# Design: G-45 — self-service money flows (ADR number: next free)

Root cause: kamra/tex/api/public.py manage_apply (~685-716) applies any price increase immediately via modification.apply (balance grows; payment optional afterwards). ManagePage.tsx:373 hides the "pay" banner when payment_status == "Pay at Hotel"; manage.higherNote tells every guest "pay it online afterwards". "Refund automatically" / "Keep as credit" both go through modification.apply; booking._refresh_booking_after_change (640-669) sets balance = total − paid (negative), payment_status "Paid"; nothing refunds or records a credit. payments.service.refund requires payment.refund capability, so guest flows cannot call it. Frontend always shows "request goes to the hotel" for a lower price (manage.lowerBody) even when the backend applies it. Also: no guard while the booking is Pending Payment/Held; amount_due_now never recomputed; currency not compared before new < old; modification.apply not idempotent on replay. Existing test asserting the gap: test_commercial_flows.TestSelfService.test_guest_extends_stay_and_lower_price_waits_for_staff (expects "applied" right after manage_apply for an increase on a card-deposit booking) — rewrite.

Decision — price increase: pay, then apply.
- collect = max(0, min(diff, required_now(new) − paid)); required_now = sum over rooms of booking.amount_due_now(result, booking.payment_method) with the new result for the changed room. Full prepay → whole difference; 30% deposit → deposit share of new total minus paid; pay-at-hotel → nothing online; existing arrears never charged by a change (cap at diff).
- collect > 0: persist a request "Awaiting Payment"; start card checkout pay.start_payment(booking=b, reservation=res, idempotency_key=f"change:{req}:{attempt}") returning to the manage page; reservation untouched. On gateway success (payments.service._after_charge, after allocation) apply the change SERVER-SIDE (never from the browser return), re-priced at the proposal's pinned sale time (pricing_sale_at) with the same total check. If it can no longer apply (sold out, reservation changed, price moved) → request Failed and the charge is refunded automatically. No card method configured → goes to staff.
- collect == 0: apply now with settlement "pay_at_hotel" (or "balance"); the proposal states "X more is payable at the hotel".
Price decrease — per Property.tex_lower_price_refund:
- Staff approval (default): persisted as a request "Requested" staff approve/reject.
- Refund automatically: apply, then refund the true overpayment max(0, paid − new booking total) (deposit-only → just a smaller balance). Refunds from successful charges on this booking, newest first, each capped by that charge's net allocation to THIS booking and provider support; keys change:{req}:refund:{txn}; refunds run in a job queued after commit (frappe.enqueue(..., enqueue_after_commit=True, now=frappe.flags.in_test)) so the @retry_on_deadlock retry on manage_apply never refunds twice. Whatever cannot be refunded (bank transfer, manual, provider error) stays as credit with the staff flag, settlement "Staff".
- Keep as credit: apply, record an explicit credit: request row settlement "Credit on booking" + amount; audit guest_change.credit; guest_change_pending = 1; booking_summary.credit = max(0, paid − total). Later increases/add-ons use it automatically (collect uses paid). Cross-stay credit ledger out of scope (separate gap).
Guards: refuse guest changes while the booking is Pending Payment or Held (PAYMENT_PENDING) and when the currency changed. One open request per reservation: a new request supersedes an Awaiting Payment one; a late payment on a superseded request is refunded.
