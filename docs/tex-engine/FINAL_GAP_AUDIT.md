# TEX Engine — Final Gap Audit (2026-09-23)

This document lists every gap that keeps a `PRODUCT_SPEC.md` requirement from being COMPLETE,
as found by the 2026-09-23 audit. The audit covered:
- five area reviews of code, tests and the running UI;
- live permission probes against the dev bench with the demo users;
- scratch tests on the pure pricing engine.

The status of each requirement is in [`IMPLEMENTATION_STATUS.md`](IMPLEMENTATION_STATUS.md).

**Severity**
- **Critical**: wrong money, or a security / tenant-isolation hole reachable today.
- **High**: a spec behaviour is missing or broken in a way that blocks real selling or exposes internal data.
- **Medium**: a spec behaviour is incomplete, or behaviour is untested where money or security depends on it.
- **Low**: polish, documentation, or minor coverage.

**Order.** The `#` column is the recommended implementation order. Critical items come first,
then High, grouped so that fixes touching the same module land together. Every fix ships with a
regression test that reproduces the defect first.

Evidence scripts and probe outputs are in the session scratchpad (`audit-a` … `audit-e`).
Probes marked **probed** were reproduced live against the bench; the others were found in code.

## 6. Implementation order

1. **Critical wave** (#1–#9). Security first (G-01, G-02, G-03, G-04), then the money defects in the pricing and booking path (G-05…G-09), each with a failing regression test first.
2. **High security wave** (#10–#16): token leak, cost exposure, role override, cross-tenant draft, allocation locks, legacy webhooks, legacy PMS routes.
3. **High commercial wave** (#17–#22): contract selection, value validation, extras inventory, versioned extras/taxes, custom domains, post-booking extras.
4. **High CRM/dashboard wave** (#23–#25).
5. **Medium** (#26–#61), in table order. Tenant-read hardening (#26) and the pricing-policy cascade (#27–#28) come first because they touch isolation and money.
6. **Low** (#62–#68).
